# 👥 Роли и процесс разработки

Как организована команда и как проходит разработка.

---

### 👥 Распределение ролей (3 разработчика)

| Роль | Ответственность | Ключевые задачи |
|:-----|:----------------|:----------------|
| **Core Developer** | C++ ядро, рендер, логика | SFML, камера, события, сборка |
| **Web/UI Developer** | Веб-интерфейс, дизайн, интеграция | HTML/CSS, кнопки, меню, JS-WASM bridge |
| **Data & Logic Developer** | Данные, граф, маршруты, квесты | JSON, A*, структура карты |

> 🔄 нужны переодические code review и т.п.

---

### 🔄 Рабочий процесс (Git Flow + GitHub)

Используем **гибридный процесс**:

1. **Задача создаётся как Issue** (с метками: `feature`, `bug`, `ui`)
2. **Создаётся ветка**: `feature/pan-zoom`, `fix/route-bug`
3. **Пишется код**, делаются коммиты(желательно прочитать пару статеек о том как это правильно делать)
4. **Открывается Pull Request** → другой участник делает **ревью** (не обязательно, но можно для практики)
5. **После одобрения** — merge в `main`
6. **Каждые ? недели** — релизная ветка: `release/v0.1`

### конвенции для типов изменений
feat: — новая функциональность

fix: — исправление ошибки

docs: — документация

style: — форматирование

refactor: — рефакторинг

test: — тесты

chore: — прочие изменения (например, .gitignore)

---

### 🏷️ Стандарты

| Аспект | Правило |
|:------|:-------|
| **Именование веток** | `feature/...`, `fix/...`, `docs/...` |
| **Сообщения коммитов** | На английском: `feat: add zoom`, `fix: camera bounds` |
| **Ревью** | Минимум 1 approve перед merge (не обязательно) |
| **Описание PR** | Что сделано, как тестировать, скриншоты (если UI) |
| **Документация** | Все новые модули — с комментариями и в `/docs` |

### 🛠️ Инструменты

| Инструмент | Назначение |
|:---------|:----------|
| **GitHub Issues** | Учёт задач |
| **GitHub Projects** | Kanban-доска: To Do → In Progress → Review → Done |
| **Milestones** | Этапы: v0.1, v0.2 |
| **Pull Requests** | Код-ревью |
| **Labels** | `bug`, `enhancement`, `help wanted`, `wip` |
